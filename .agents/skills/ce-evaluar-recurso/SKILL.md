# ce-evaluar-recurso

1. Definir qué necesidad empresarial concreta se busca resolver. Buscar primero si Obsidian nativo (Bases, Properties, Templates, CLI) o el motor actual ya lo hace.
2. Inspectar fuente original: URL/release/commit/versiones, mantenibilidad, APIs, dependencias, licencia de código/plantillas/medios y seguridad. No inferir compatibilidad por un video.
3. Para `obsmd-projects/obsidian-projects`: archivado en GitHub y discontinuado en 2025; **no instalar** ni copiar código sin análisis de licencias. Considerar únicamente patrón de vistas y plantillas.
4. Comparar necesidad, función existente, riesgo, costo, alternativa sin plugin, reversibilidad, prueba visual y casos de migración.
5. Preparar una ficha de investigación con evidencia de fuentes y un experimento sintético, no copiar código ni dar por aprobada la tecnología.
6. Solicitar decisión humana para añadir dependencia; pruebas en instalación aislada y desinstalación sin pérdida del conocimiento.
**Salida:** adoptar/adaptar/rechazar/pendiente con pruebas faltantes y licencia.
